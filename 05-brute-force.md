# Brute Force — Attack & Detection

**Attack #4 of 5** · [Back to overview](../README.md)

## What this attack is

Brute forcing is the mirror image of password spraying:

| | Password Spraying | Brute Force |
|---|---|---|
| **Targets** | Many usernames | One username |
| **Guesses** | One password (or a couple) | Many passwords |
| **Why attackers use it** | Avoids locking out any single account | Works when there's no lockout policy, or the attacker only cares about one specific, valuable account |

Where spraying spreads a small number of guesses wide across many accounts, brute forcing picks **one account** and grinds through a long list of passwords until one works. It's noisier against that one account, but it's the right tool when an attacker has a specific target in mind, for example, a known admin account, rather than just "any account that lets me in."

## How I ran it

### Step 1: Build a guess list

I created a list of common, realistic weak passwords, the kind that show up constantly in real breach data, with the real password deliberately placed near the end rather than first. This simulates not knowing the password in advance, the way a real attacker grinds through a list without knowing which entry (if any) will work:

```
Password123
letmein1
Qwerty123!
Welcome1!
Football123
Admin@123
Spring2025!
Iloveyou1!
Summer2026!
Autumn2024!
```

![Password list created with nano](../screenshots/26-brute-passwords-list.png)

### Step 2: Run the attack

I used `netexec`, the same tool from the password spraying attack, just with the username and password list **swapped around**:

```
netexec smb 10.10.10.10 -u caramel -p brute-passwords.txt
```

- **`-u caramel`** — one fixed username (singular `-u`, unlike spraying's `-u users.txt` which took a whole list)
- **`-p brute-passwords.txt`** — now the **list** goes here instead of the username list

## Checking the detection side

```
index=main host=DC01 source="WinEventLog:Security" EventCode=4776 Logon_Account="caramel" earliest=-30m
```

This pulled up the matching events, all tied to the same account, `caramel`, clustered within a fraction of a second of each other.

### The successful attempt

```
EventCode=4776
TaskCategory=Credential Validation
Keywords=Audit Success
Logon Account:  caramel
Error Code:     0x0
Time: 10:27:59.578 AM
```

![Successful 4776 event for caramel, Error Code 0x0](../screenshots/28-splunk-4776-success.png)

### One of the failed attempts, right before it

```
EventCode=4776
TaskCategory=Credential Validation
Keywords=Audit Failure
Logon Account:  caramel
Error Code:     0xC000006A
Time: 10:27:59.553 AM
```

![Failed 4776 event for caramel, Error Code 0xC000006A](../screenshots/29-splunk-4776-failure.png)

## Reading these two events together

Placed side by side, these two log entries tell the whole story:

| | Failed attempt | Successful attempt |
|---|---|---|
| **Keywords** | `Audit Failure` | `Audit Success` |
| **Error Code** | `0xC000006A` (wrong password) | `0x0` (success) |
| **Timestamp** | `10:27:59.553 AM` | `10:27:59.578 AM` |

The two timestamps are only **25 milliseconds apart**. A real person could never type a login attempt that fast, this gap is the clearest possible proof that these attempts were generated by an automated tool, not a human fumbling their password. That tight timing, repeated against the exact same account, is the real signature of brute forcing.

## Comparing this to password spraying

This is the most useful part to understand, since both attacks use the exact same event ID (`4776`), but the *pattern* each one produces is completely different:

- **Password spraying**: many **different** `Logon Account` values, usually just one or two attempts each, all within the same short window
- **Brute forcing**: the **same** `Logon Account` value, repeated many times in a row, in a very tight window

A real detection rule has to look for different things depending on which pattern it's hunting:
- **Spray detection**: count *distinct usernames* with 4776 failures in a short window
- **Brute force detection**: count *repeated failures on the same username* in a short window

Same event ID, same log source, two different detection rules, because the thing that makes each one suspicious is the pattern across multiple events, not any single event on its own.

## Problems I ran into (left in on purpose)

**Hydra failed against this target entirely.**
I first tried Hydra, the "classic" brute-force tool, since it's the standard answer whenever brute force comes up:
```
hydra -l caramel -P brute-passwords.txt smb://10.10.10.10
→ [ERROR] invalid reply from target smb://10.10.10.10:445/
```
This turned out to be a real compatibility issue, not something fixable with a quick flag. Hydra's SMB module doesn't correctly understand Windows Server 2022's SMB implementation, even on the latest Hydra version. I also tried `winrm://`, which failed with `[ERROR] Unknown service: winrm`, that protocol module isn't supported in this Hydra build at all. I switched to `netexec`, a more actively maintained tool that had already proven reliable in this lab during password spraying.

**I brute-forced the wrong username first.**
My first attempt targeted `clatte`, a username that doesn't actually exist in this domain. Windows gave the exact same `STATUS_LOGON_FAILURE` message for every single guess, including what I thought was the "correct" password. This is intentional security design: Windows deliberately gives identical error messages for "wrong username" and "wrong password," so an attacker (or in this case, me) can't use the error message to tell which one they got wrong. I only caught the mistake by double-checking my own list of real usernames. Lesson: **don't trust "it's failing" to mean "the password's wrong"**, it might mean the account doesn't exist at all.

## Takeaways

- The *pattern* across multiple log entries matters more than any single event, the same event ID (4776) means something different depending on whether it repeats on one account or spreads across many
- Millisecond-level timestamps are a strong, simple signal for distinguishing automated tooling from a real person
- Tool compatibility is a real part of offensive security work, Hydra, often the "default" brute-force tool, simply didn't work here, and recognizing that quickly (rather than fighting it) mattered more than forcing one specific tool to work
- Windows' identical failure messages for "wrong username" and "wrong password" are a deliberate security feature, but they can just as easily trip up the attacker (me) as they're meant to slow down a real one
